# Single Source of Truth

## 1. Статус документа

Этот документ — нормативная карта владения данными и runtime-инвариантов
`clash-sheet-sync-bot`.

Он отвечает на четыре вопроса:

1. Где находится авторитетное значение каждого класса данных.
2. Какие данные являются копиями, snapshots или служебными зеркалами.
3. Как разрешаются расхождения между источниками.
4. Какие гарантии обязаны сохранять изменения кода.

`SSOT.md` описывает текущее реализованное поведение. Это не roadmap и не
спецификация будущих функций.

Иерархия проектной документации:

1. `SSOT.md` — владение данными, приоритеты и обязательные инварианты.
2. [`docs/architecture.md`](docs/architecture.md) — устройство и потоки
   реализации.
3. [`docs/operations.md`](docs/operations.md) — эксплуатация, backup, restore и
   диагностика.
4. [`README.md`](README.md) — обзор, установка и базовый запуск.

Если реализация, тесты и этот документ расходятся, расхождение считается
дефектом. Его нельзя молча закреплять: нужно явно выбрать правильный контракт,
после чего согласованно изменить код, тесты и документацию.

## 2. Главный принцип

В системе нет одного физического файла, являющегося источником истины для всех
данных. Авторитет распределён по предметным областям.

SQLite — главный **runtime source of truth**, но не источник игровых данных,
ручных пользовательских значений, актуальных Telegram-прав или секретов
процесса.

| Предметная область | Авторитетный источник | Неавторитетные копии |
|---|---|---|
| Настройки Telegram-групп и их lifecycle | SQLite | Telegram UI, отчёты |
| Привязки Google Sheets | SQLite | `_bot_state`, URL в сообщениях |
| Tracked clans и их порядок | SQLite | Отрисованные блоки Google Sheets |
| Профили колонок | SQLite | Заголовки и форматирование Google Sheets |
| Runtime-state и история sync | SQLite | Telegram-отчёты |
| Ручные значения в user-колонках | Google Sheets | `user_values_json` в SQLite |
| Текущий состав кланов и технические поля игроков | Clash of Clans API | SQLite и Google Sheets |
| Текущие CWL group/war/attack data | Clash of Clans API | `technical_values_json` и Google Sheets |
| Актуальные права администратора группы | Telegram Bot API | Положительный cache в SQLite |
| ID единственного superadmin | Environment или `.env` | `AppConfig` в памяти |
| Группа техподдержки и история рассылок | SQLite | Telegram-кнопки и сообщения |
| Конфигурация процесса | Environment, затем `.env`, затем defaults | `AppConfig` в памяти |
| Google service account identity и ключ | `credentials.json` | Ожидаемый email в `.env` |
| Структура SQLite | `clash_sheet_sync_bot/migrations.py` | Схема конкретного файла БД |

## 3. Термины

**Авторитетный источник** — место, значение из которого должно победить при
разрешении допустимого конфликта.

**Runtime-state** — настройки и состояние, необходимые боту для принятия
решений между Telegram updates и запусками процесса.

**Snapshot/cache** — сохранённая копия авторитетных данных. Она может
использоваться для сравнения, восстановления пользовательских значений,
межсезонного отображения или снижения числа внешних запросов, но не меняет
владельца исходного поля.

**Служебное зеркало** — копия данных рядом с внешним ресурсом для диагностики и
восстановления связи. Зеркало не становится владельцем данных.

**Managed block** — прямоугольная область Google Sheets, которой управляет бот
и координаты которой зарегистрированы в SQLite.

## 4. SQLite: runtime source of truth

### 4.1. Физическое расположение

SQLite-файл задаётся `DB_PATH`. Значение по умолчанию — `bot.db`, но имя файла
не является частью доменного контракта.

При WAL-режиме `*.db-wal` и `*.db-shm` являются частями текущего физического
состояния SQLite. Их нельзя рассматривать как отдельные источники данных.

### 4.2. Владение таблиц

| SQLite-таблица | Авторитетные данные |
|---|---|
| `telegram_chats` | Известные чаты, setup-state, статус настройки и последний sync summary |
| `chat_admin_links` | Связи пользователей с группами и положительный admin cache |
| `setup_tokens` | Lifecycle одноразовых токенов подключения |
| `transfer_tokens` | Lifecycle одноразовых токенов переноса |
| `bot_users` | Известные личные пользователи, активность и ожидаемое admin-действие |
| `bot_settings` | Текущая группа и ссылка техподдержки |
| `support_setup_tokens` | Lifecycle одноразовых токенов подключения техподдержки |
| `broadcasts` | Текст, статус и итоговые счётчики массовых рассылок |
| `sheet_bindings` | Активная привязка чата, spreadsheet ID, имена/ID служебных листов, timezone, активный CWL-сезон |
| `tracked_clans` | Набор отслеживаемых кланов, active flag и порядок |
| `column_profiles` | Ключи, заголовки, типы, видимость и порядок колонок |
| `composition_player_state` | Последнее известное состояние игрока и snapshot его user-values |
| `cwl_row_state` | История CWL-строк, technical snapshot и snapshot user-values |
| `sheet_blocks` | Реестр областей Google Sheets, управляемых ботом |
| `sync_runs` | История принятых запусков `/sync`, их результат и ошибки |
| `schema_migrations` | Применённые версии схемы |

SQLite определяет, какие группы, таблицы, кланы, профили и блоки бот считает
своими. Ручное изменение соответствующих технических данных в Google Sheets не
меняет runtime-конфигурацию.

### 4.3. Схема и миграции

Нормативное описание схемы и последовательности её обновления находится в
`clash_sheet_sync_bot/migrations.py`.

- `SCHEMA_VERSION` задаёт текущую ожидаемую версию.
- Миграции применяются при старте до обработки Telegram updates.
- Production-схема не изменяется ручным SQL без соответствующей миграции.
- Legacy data не удаляются без отдельного решения, миграции и теста.

Старый файл БД является экземпляром runtime-state, а не спецификацией схемы.

## 5. Google Sheets: user workspace

### 5.1. Авторитетные данные

Google Sheets является авторитетным источником ручных значений в активных
`user`-колонках зарегистрированных managed blocks.

Перед перезаписью блоков бот:

1. читает зарегистрированные в SQLite managed blocks;
2. сопоставляет строки по `__bot_key`;
3. импортирует значения `user`-колонок;
4. объединяет их с сохранённым snapshot;
5. строит новое состояние;
6. перезаписывает только управляемые области.

Импортированное значение, включая намеренно очищенную ячейку, перекрывает
предыдущий snapshot этого поля в SQLite.

Для CWL действует отдельное производное правило: если импортированное значение
пусто, бот может заполнить его непустым значением одноимённой видимой
user-колонки состава этого игрока. Связь строится по нормализованному заголовку,
а не по `column_key`. Поэтому очистка CWL-ячейки не гарантирует, что она
останется пустой, пока связанное значение состава заполнено.

Наличие строки в managed block может быть пользовательским входом в lifecycle,
но не делает весь лист владельцем runtime-state. В частности, если ранее
вышедший игрок удалён пользователем из прочитанного блока вышедших, при
следующем успешном sync его сохранённый status переходит из `exited` в
`untracked`. Итоговое состояние фиксируется в SQLite.

### 5.2. Неавторитетные данные

Следующие данные в Google Sheets не являются источником runtime-настроек:

- tracked clans;
- порядок и active status кланов;
- конфигурация профилей колонок;
- технические значения состава и CWL;
- chat binding;
- sync history;
- координаты managed blocks.

Ручная правка технической колонки может быть использована только как
ограниченный fallback для идентификации строки при повреждённом `__bot_key`.
При следующем успешном sync техническое значение восстанавливается из
авторитетного источника.

### 5.3. Границы владения

Бот имеет право изменять:

- зарегистрированные managed blocks;
- обязательные листы `Состав`, активный `CWL` и `_bot_state` в рамках их
  служебного контракта;
- staging- и архивные CWL-листы, созданные его pipeline;
- форматирование и скрытие служебных колонок внутри управляемых областей.

Произвольные пользовательские области вне managed blocks боту не принадлежат.

## 6. Clash of Clans API: technical source

Clash of Clans API является авторитетным источником текущих игровых данных.

Для состава это:

- membership активных tracked clans;
- player tag;
- nickname;
- town hall;
- clan tag.

Для CWL это:

- league group и season;
- rounds и war tags;
- wars и attacks;
- stars и destruction percentage;
- технические данные участников и соперников.

SQLite и Google Sheets содержат snapshots или представления этих данных.
Ручное изменение технического значения в таблице или устаревшее значение в
SQLite не перекрывает успешный ответ CoC API.

Если необходимые текущие данные CoC API недоступны, sync завершается ошибкой до
write-фазы. Бот не выдаёт устаревший snapshot за актуальный ответ. Исключение —
явный межсезонный CWL-режим: когда активные кланы сейчас не участвуют в CWL,
бот показывает последний подходящий сезон из SQLite и помечает его как
предыдущий.

## 7. Telegram Bot API: access source

Telegram Bot API является авторитетным источником текущего статуса участника
группы.

Для чувствительных действий выполняется fresh admin check. Результат fresh
check перекрывает положительный cache из `chat_admin_links`.

Положительный cache допустим только для обычной навигации по меню и действует в
пределах `ADMIN_CACHE_TTL_SECONDS`. Ошибка Telegram API при fresh check не
подтверждает права и поэтому не разрешает чувствительное действие.

К чувствительным действиям относятся как минимум:

- привязка, смена и отвязка таблицы;
- диагностика и auto-fix;
- создание transfer token;
- добавление, удаление и перемещение кланов;
- создание, переименование, удаление и перемещение колонок.

Доступ к меню техподдержки и рассылок определяется только точным совпадением
Telegram `user.id` с обязательным `SUPERADMIN_USER_ID`. Видимость кнопки не
является проверкой доступа: каждый admin callback и команда подключения
техподдержки валидируют ID повторно. Подключающий техподдержку superadmin также
должен быть актуальным администратором выбранной группы.

## 8. Конфигурация процесса и секреты

Приоритет конфигурации:

1. уже заданная переменная окружения процесса;
2. значение из `.env`;
3. программный default для необязательного параметра.

Обязательные значения без default:

- `TELEGRAM_BOT_TOKEN`;
- `COC_API_TOKEN`;
- `GOOGLE_SERVICE_ACCOUNT_FILE`.
- `SUPERADMIN_USER_ID`.

`credentials.json` или другой файл по `GOOGLE_SERVICE_ACCOUNT_FILE` является
авторитетным источником ключа и `client_email` Google service account.
`GOOGLE_SERVICE_ACCOUNT_EMAIL` — необязательная проверка ожидаемой identity, а
не замена credentials.

`.env`, credentials, токены и содержимое production-БД не входят в
нормативную документацию и не коммитятся.

## 9. Копии, snapshots и зеркала

### 9.1. User-values в SQLite

`composition_player_state.user_values_json` и
`cwl_row_state.user_values_json` хранят последний известный snapshot ручных
значений. Он нужен для:

- переноса значений между перезаписями managed blocks;
- переходов игрока между active/exited состояниями;
- связи совместимых пользовательских колонок;
- CWL row-key migrations и fallback;
- межсезонного отображения.

Если актуальную строку удалось импортировать из Google Sheets, её ручные
значения имеют приоритет над SQLite snapshot. Значения других профилей, которых
нет в импортируемом блоке, сохраняются в snapshot и не стираются случайно.

### 9.2. Technical values в SQLite

Технические значения в composition/CWL state нужны для истории, diff,
стабильного планирования и межсезонного CWL fallback. Для текущего sync они не
перекрывают успешный ответ CoC API.

### 9.3. `_bot_state`

Скрытый лист `_bot_state` — служебное зеркало binding рядом с Google-таблицей.
Он используется для:

- диагностики соответствия таблицы SQLite binding;
- хранения идентификаторов обязательных листов рядом с таблицей;
- проверки write/batchUpdate доступа;
- восстановления служебного листа и его метаданных через auto-fix.

SQLite binding имеет приоритет над `_bot_state`. При auto-fix `_bot_state`
перезаписывается из SQLite и фактических metadata обязательных листов.
Несовпадение `google_sheet_id` считается ошибкой диагностики и не исправляется
молчаливо.

### 9.4. `sheet_blocks`

`sheet_blocks` — авторитетный реестр областей, которыми намерен управлять бот.
Фактическая Google-таблица остаётся физической реальностью, поэтому удаление,
переименование или перемещение листа может сделать metadata устаревшими.

Такое расхождение не передаёт боту владение произвольной новой областью.
Диагностика и auto-fix должны восстановить обязательные листы и служебные
связи, после чего успешный sync обновляет metadata managed blocks.

## 10. Разрешение конфликтов

| Конфликт | Побеждает | Поведение |
|---|---|---|
| CoC API и сохранённое technical value | CoC API | Новое значение записывается в представление и SQLite snapshot |
| User-cell в managed block и SQLite snapshot | Google Sheets | Импортированное значение переносится в planned state |
| Пустая CWL user-cell и одноимённое непустое значение состава | Значение состава | CWL получает производное значение по совпадающему заголовку |
| Конфигурация колонок в SQLite и ручной заголовок/порядок в Sheets | SQLite | Следующий sync восстанавливает настроенное представление |
| Sheet binding в SQLite и `_bot_state` | SQLite | Диагностика сообщает mismatch; auto-fix переписывает зеркало |
| Fresh Telegram admin check и cache | Fresh check | Чувствительное действие разрешается только по свежему результату |
| Environment и `.env` | Environment | `load_dotenv(..., override=False)` не заменяет переменную процесса |
| Текущая схема кода и старая схема БД | Миграции | При старте применяются отсутствующие версии |
| Корректный `__bot_key` и видимые поля строки | `__bot_key` | Видимые поля используются только как безопасный fallback |
| Два разных CWL season в одном sync | Ни один | Sync останавливается до записи |

Повреждённый или неоднозначный идентификатор строки не разрешает угадывать
значение. Бот применяет только предусмотренный строгий fallback, добавляет
warning либо пропускает строку.

## 11. Идентичность и ключи

Основные идентификаторы:

- `chat_id` — identity Telegram-чата;
- `google_sheet_id` — identity Google Spreadsheet;
- нормализованный `clan_tag` — identity клана;
- нормализованный `player_tag` — identity игрока;
- `column_key` — стабильная identity колонки внутри профиля;
- `__bot_key` — стабильная identity строки Google Sheets;
- CWL `row_key` — identity строки сезона, клана, раунда, игрока и marker;
- `block_key` — identity managed block внутри листа.

Отображаемые названия, nickname, заголовки и координаты строк не заменяют
стабильные ключи.

Одна Google-таблица может иметь не более одной активной привязки. Это
обеспечивается SQLite unique index по `google_sheet_id` для active bindings.

## 12. Sync и границы транзакции

`/sync` использует staged pipeline:

```text
создать sync run
        ↓
загрузить runtime config из SQLite
        ↓
подготовить composition из SQLite + Sheets + CoC API
        ↓
подготовить CWL из SQLite + Sheets + CoC API
        ↓
записать composition в Google Sheets
        ↓
записать CWL и _bot_state в Google Sheets
        ↓
сохранить SQLite state и commit
        ↓
отправить Telegram report
```

Google Sheets и SQLite не образуют общей распределённой транзакции.

- Ошибка на preparation-фазе не должна изменять Google Sheets.
- После начала write-фазы таблица может быть изменена частично.
- При ошибке write-фазы незакоммиченные SQLite-изменения откатываются.
- Ошибка после начала записи обязана сопровождаться partial write warning.
- После partial write пользователь должен запустить диагностику и повторить
  `/sync`.
- Ошибка доставки Telegram report после успешного SQLite commit не откатывает
  успешный sync.
- Успешный пользовательский report содержит только обновлённые разделы,
  названия отслеживаемых кланов, строку `Разработчик: BangkokToD` и, если
  техподдержка настроена, ссылку `Чат Леши`.
- Recoverable warnings успешного sync сохраняются в `sync_runs.report_json`,
  но не добавляются в компактный пользовательский report.

## 13. Concurrency

В одном процессе действуют:

- chat lock — не допускает два одновременных sync одного чата;
- sheet lock — не допускает две одновременные записи одной Google-таблицы;
- global semaphore — ограничивает общее число параллельных sync.

Эти примитивы process-local. Запуск нескольких процессов бота с одним Telegram
token или общей runtime-БД не является поддерживаемой моделью и не должен
использоваться как способ масштабирования.

`DEV_MODE=True` отключает только последовательный cooldown. Он не отключает
locks и global semaphore.

## 14. Обязательные инварианты

Любое изменение должно сохранять следующие правила:

1. SQLite остаётся runtime source of truth.
2. Google Sheets остаётся владельцем ручных user-values.
3. CoC API остаётся владельцем текущих technical values.
4. Fresh Telegram API check остаётся владельцем решения о чувствительном
   доступе.
5. Бот не пишет в произвольные пользовательские области вне managed blocks.
6. `__bot_key` остаётся основным ключом строки.
7. Preparation завершается до первой записи sync в Google Sheets.
8. Ошибка после начала записи даёт partial write warning.
9. Один чат и одна таблица не получают конкурирующие записи внутри процесса.
10. Один active CWL-лист не смешивает разные seasons.
11. Telegram delivery failure после SQLite commit не меняет success на error.
12. Изменение схемы SQLite проходит через версионированную миграцию.
13. Секреты и production-state не попадают в Git.

## 15. Legacy и совместимость

- `sync_settings.json` больше не является runtime source и игнорируется
  актуальным кодом.
- Legacy table type `composition` сохраняется только для миграции и обратной
  совместимости. Актуальные профили: `composition_active`,
  `composition_exited` и `cwl`.
- Корневой `bot.py` — compatibility launcher. Runtime-код находится в package
  `clash_sheet_sync_bot`.

Legacy-артефакт не становится источником истины только потому, что физически
присутствует рядом с приложением.

## 16. Backup, restore и потеря данных

Для полного восстановления production недостаточно только Git-репозитория.
Нужно отдельно сохранять:

- SQLite database с учётом WAL;
- `.env`;
- Google service account credentials;
- пользовательские Google Sheets.

Потеря SQLite означает потерю runtime-конфигурации, привязок, state и истории.
Google Sheets может сохранить пользовательские значения, но не является
полной резервной копией SQLite.

Потеря или повреждение Google Sheets может привести к потере ручных значений,
которые ещё не были успешно импортированы в SQLite snapshot. SQLite snapshot
не заменяет штатный backup пользовательской таблицы.

Практические процедуры описаны в
[`docs/operations.md`](docs/operations.md).

## 17. Правило изменения SSOT

Изменение владельца данных, приоритета источников или любого инварианта из
этого документа является архитектурным изменением.

Такое изменение должно включать:

1. явное обновление `SSOT.md`;
2. изменение реализации;
3. тесты на новый контракт и конфликтные сценарии;
4. при необходимости миграцию существующего runtime-state;
5. синхронизацию `docs/architecture.md`, `docs/operations.md`, README и
   changelog.

Новая копия данных должна сразу получить классификацию: авторитетный источник,
snapshot/cache, служебное зеркало либо производное представление.
