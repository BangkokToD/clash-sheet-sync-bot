# Техническое задание: прогноз ЛВК

## 1. Цель

Добавить Telegram-команду `/cwl_forecast`, которая для каждого подключённого
к Telegram-группе клана показывает:

- фактический состав нашего клана в текущей войне ЛВК;
- фактический состав текущего соперника;
- потенциальную силу составов всех оставшихся соперников по раундам.

Потенциальный состав — это сильнейшие зарегистрированные в League Group
игроки соперника, ограниченные размером нашей команды в текущей или ближайшей
подготавливаемой войне. Это оценка сложности, а не утверждение о точном
будущем составе.

## 2. Источники данных

Используются только официальные ручки Clash of Clans API:

```text
GET /clans/{clanTag}/currentwar/leaguegroup
GET /clanwarleagues/wars/{warTag}
```

League Group является источником зарегистрированных участников, сезона,
клана, уровня клана и известных `warTag`. CWL War является источником
`state`, `teamSize`, фактических сторон войны, `mapPosition` и уровней ратуш.

Будущие раунды с `warTag == "#0"` связываются с соперниками только по
подтверждённому администратором расписанию. Запрещено выводить расписание из
порядка `clans`, угадывать round-robin алгоритм, использовать OCR или
неофициальные API.

## 3. `/cwl_forecast`

### 3.1. Доступ

- Команда работает только в подключённой группе или супергруппе Telegram.
- Запустить её может любой участник группы.
- Обрабатываются все активные кланы группы в порядке `sort_order`.
- На каждый подходящий клан отправляется отдельное сообщение.

### 3.2. Выбор войны

Для каждого клана:

1. получить League Group;
2. найти среди уже созданных войн войну с нашим кланом в состоянии `inWar`;
3. если такой нет — выбрать ближайшую войну с нашим кланом в состоянии
   `preparation`;
4. если активной или подготавливаемой войны нет, прогноз для клана не
   отправлять.

Ближайшая `preparation` определяется по API-времени начала; при равенстве
используется номер раунда, затем нормализованный `warTag` как стабильный
tie-breaker. Нельзя полагаться на порядок ответов HTTP.

Во время последней `inWar` или `preparation` показываются только наш состав и
текущий соперник: ручное расписание не требуется.

### 3.3. Размер и порядок составов

- `teamSize` выбранной войны задаёт высоту всей матрицы.
- Наш фактический состав и фактический состав текущего соперника берутся из
  выбранной войны и сортируются по `townhallLevel DESC`, затем по
  нормализованному player tag `ASC`; `mapPosition` остаётся обязательным
  полем API, но не задаёт порядок строк.
- Для каждого будущего соперника участники берутся из `clans[].members`
  League Group и сортируются по:
  1. `townHallLevel DESC`;
  2. нормализованный player tag `ASC`.
- Из будущего состава берутся первые `teamSize` игроков.
- Если зарегистрированных игроков меньше `teamSize`, отсутствующие позиции
  дополняются символом `—`.
- Некорректные обязательные поля внешнего ответа нельзя молча пропускать:
  ошибка относится к конкретному клану и попадает в итоговую сводку ошибок.

### 3.4. Формат сообщения

Одно сообщение на клан, даже если Telegram визуально переносит строки.

```text
Название клана | #ТЕГ
[щит]  [война]  4️⃣  5️⃣  6️⃣  7️⃣
[TH]|[TH]|[TH]|[TH]|[TH]|[TH]
[TH]|[TH]|[TH]|[TH]|[TH]|[TH]
...
[sum]  [sum]  [sum]  [sum]  [sum]  [sum]
```

Контракты форматирования:

- заголовок: актуальное API-название нашего клана, ` | `, нормализованный тег;
- в строке заголовков колонок нет `|`;
- между каждым элементом заголовка ровно два обычных пробела;
- первая колонка — `defense_shield`;
- вторая — `clan_war`;
- далее — стандартные Unicode keycap-цифры оставшихся раундов;
- в строках матрицы нет пробелов вокруг `|`;
- показываются только эмодзи ратуш и `—`, без имён игроков;
- после матрицы идёт plain-строка сумм уровней ратуш по колонкам;
- между суммами ровно два обычных пробела, а `—` добавляет к сумме `0`;
- HTML/Markdown parse mode для такого сообщения не используется;
- пользовательское название клана не должно ломать формат или entities.

### 3.5. Premium emoji и fallback

- Загружать существующий `resources/telegram_emoji_catalog.json` один раз при
  старте приложения.
- Валидировать `schema_version == 1`, обязательные ключи, все TH 1–18,
  цифровые и уникальные `custom_emoji_id`, непустые fallback-поля.
- Основное сообщение отправлять через Telegram Bot API `entities` типа
  `custom_emoji`; offsets и lengths рассчитывать в UTF-16 code units.
- В тексте с entities использовать поле `fallback` каталога.
- Не совмещать `parse_mode` и `entities`.
- Если Telegram ответил HTTP 400 на сообщение с custom emoji entities,
  повторить отправку ровно один раз обычным текстом, используя
  `fallback_text`.
- Не повторять fallback-отправку при сетевой ошибке, 401, 403, 429 или 5xx.

## 4. Ручное расписание `/cwl_forecast_schedule`

### 4.1. Доступ и назначение

- Это отдельная команда.
- Её могут использовать только creator/admin текущей подключённой группы.
- Права проверяются свежим запросом при приёме команды и при каждом callback.
- Команда не принимает изображения и не запускает OCR.
- Если в группе несколько активных CWL-кланов, сначала предлагается выбрать
  наш клан.

### 4.2. Кнопочный ввод

- Уже известные по реальному `warTag` раунды заполняются автоматически и
  недоступны для редактирования.
- Для каждого будущего раунда с `warTag == "#0"` администратор выбирает
  соперника кнопкой.
- Одна кнопка занимает одну строку и содержит актуальные API-данные:

```text
Clan name · ур. 19 · #TAG
```

- Уже выбранный соперник удаляется из следующих вариантов.
- Наш клан никогда не предлагается как соперник.
- Callback data содержит только компактный ID сессии, действие и индекс/ID,
  безопасные для лимита Telegram 64 bytes; название клана в callback data не
  помещается.
- Перед записью показывается полное расписание раундов и кнопки
  `Подтвердить`, `Назад`, `Отмена`.
- Повторный запуск команды позволяет редактировать существующее расписание,
  но изменяемыми остаются только раунды, у которых в свежем API всё ещё `#0`.

### 4.3. Сессия

- Одновременно допускается одна активная сессия для глобального ключа
  расписания.
- TTL сессии — настраиваемые 600 секунд по умолчанию.
- Истёкшая сессия удаляется/заменяется транзакционно.
- Каждый callback повторно проверяет: TTL, администратора, chat, пользователя
  сессии и актуальность League Group.
- Чужой пользователь, другой chat или просроченная сессия не могут изменить
  черновик.

### 4.4. Хранение и совместное использование

Расписание глобально переиспользуется всеми подключёнными Telegram-группами,
которые обращаются к той же ЛВК. Ключ:

```text
season + group_fingerprint + clan_tag
```

`group_fingerprint` — стабильный hash отсортированных нормализованных тегов
всех кланов League Group. Названия, уровни и порядок массива `clans` в hash не
входят.

Хранятся только теги соперников по раундам и audit metadata. Названия и уровни
кланов всегда обновляются из свежего API.

Audit metadata минимум:

- `created_by_user_id`;
- `source_chat_id`;
- `created_at`;
- `updated_at`.

Новый сезон или другой fingerprint не переиспользует старое расписание.
Удалять старые строки в рамках этой функции не требуется.

### 4.5. Валидация расписания

При каждом `/cwl_forecast` сохранённое расписание сверяется со всеми уже
появившимися реальными войнами:

- каждый соперник принадлежит той же League Group;
- соперники не повторяются;
- наш клан не указан соперником;
- API-известная пара для раунда совпадает с сохранённой;
- количество и номера раундов согласованы с League Group.

При конфликте расписание не исправляется автоматически и прогноз для этого
клана не отправляется. Пользователю сообщается, что администратору нужно снова
выполнить `/cwl_forecast_schedule`.

Если для требуемых `#0` раундов полного валидного расписания нет, частичный
прогноз для клана запрещён. Сообщение:

```text
Для клана NeverNight не заполнено расписание будущих раундов ЛВК. Администратор группы должен выполнить команду /cwl_forecast_schedule.
```

Другие готовые кланы группы при этом продолжают обрабатываться.

## 5. Cooldown и параллельность

- Отдельный cooldown `/cwl_forecast`: конфигурируемые 60 секунд по умолчанию.
- Cooldown начинается в момент принятия команды до внешних API-запросов.
- Он учитывается даже при отсутствии ЛВК, расписания или при ошибке.
- Cooldown хранится в SQLite и переживает restart процесса.
- `DEV_MODE=True` отключает только временной cooldown, но не singleflight.
- В одном chat одновременно формируется не более одного прогноза.
- Параллельный повтор получает точный текст:

```text
Прогноз ЛВК уже формируется
```

- Повтор в пределах cooldown получает:

```text
Прогноз ЛВК недавно запускался. Повторить можно через N сек.
```

## 6. Частичные ошибки и тишина

- Успешные прогнозы отправляются первыми.
- Затем отправляется одно краткое сообщение со списком кланов, обработка
  которых завершилась технической ошибкой.
- Отсутствующее/конфликтное расписание — пользовательское состояние, а не
  техническая ошибка; для него используется отдельная инструкция админу.
- Кланы без активной/подготавливаемой ЛВК молча пропускаются.
- Если все кланы молча пропущены, бот не отправляет итоговое сообщение.
- Принятый cooldown при этом сохраняется.

## 7. Хранение и миграция

- SQLite остаётся runtime SSOT.
- Не переиспользовать `telegram_chats.setup_state`.
- Добавить отдельное состояние cooldown, сохранённые расписания, строки
  раундов и временные сессии.
- Следующая migration должна использовать следующий свободный schema version;
  на проверенном HEAD это версия 8.
- Миграция должна быть идемпотентной в рамках существующего migration runner и
  корректно обновлять базу версии 7.

## 8. Конфигурация

Добавить в `AppConfig` и `.env.example` минимум:

```text
CWL_FORECAST_COOLDOWN_SECONDS=60
CWL_FORECAST_SCHEDULE_TTL_SECONDS=600
```

Переиспользовать существующий `CWL_WAR_CONCURRENCY_LIMIT`; новый дублирующий
лимит запросов не вводить.

## 9. Совместимость и ограничения

- Python 3.12, полные type hints.
- Русские Google-style docstrings для публичной новой логики.
- Строгий parsing внешних данных; `bool` не считается допустимым `int`.
- Не добавлять OCR/runtime-зависимости.
- Не менять действующие `/sync`, setup, Sheet layout, transfer и CWL sync
  контракты без отдельного требования.
- Глобальные расписания не принадлежат Telegram chat, поэтому transfer chat не
  переносит и не удаляет их. Cooldown остаётся состоянием конкретного chat.

## 10. Критерии приёмки

Функция принята, если:

1. оба command flow соответствуют требованиям выше;
2. администратор один раз задаёт расписание кнопками без OCR;
3. обычный пользователь не может изменить расписание;
4. прогноз не публикует неполные будущие раунды;
5. actual и predicted rosters имеют правильный порядок и высоту `teamSize`;
6. premium emoji корректны, а HTTP 400 fallback работает;
7. cooldown, restart и singleflight покрыты тестами;
8. partial error не скрывает успешные кланы;
9. миграция проверена на пустой БД и upgrade с версии 7;
10. полный CI quality gate проходит;
11. документация и версия обновлены до `1.1.0`;
12. нет push, tag, release или deploy без отдельного разрешения.
