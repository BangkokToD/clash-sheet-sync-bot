## 2. Цель

Добавить в существующий `/sync` учёт рейдовых уикендов Clan Capital с одним
понятным коэффициентом результата для каждого участвовавшего игрового аккаунта.

Пользователь должен видеть:

- сколько атак из обязательных шести использовал игрок;
- сколько нормо-очков принесли его атаки;
- итоговый коэффициент рейдового уикенда;
- добытое золото столицы;
- рейтинг игроков по коэффициенту;
- красную подсветку ячейки `Атаки`, если завершивший уикенд игрок не использовал
  все шесть атак.

Бот не должен выводить в Google Sheets порайонный журнал или отдельную строку
каждой атаки.

## 3. Термины

- **Рейдовый сезон / уикенд** — один элемент ответа
  `/clans/{clanTag}/capitalraidseasons`, идентифицируемый каноническим
  `startTime`. Внутренний `season_key` — нормализованный UTC timestamp, а дата
  в названии архива — его UTC calendar date.
- **Активный лист** — лист Google Sheets с каноническим названием `Рейды`.
- **Архивный лист** — сохранённый лист конкретного уикенда с названием
  `Рейды YYYY-MM-DD`.
- **Участник** — игрок, присутствующий в `members` соответствующего элемента
  API. Игроки текущего состава, отсутствующие в `members`, в рейдовый лист не
  добавляются.
- **Обычный район** — любой район, кроме Столицы (`Capital Peak`).
- **Столица** — район `Capital Peak`, определяемый по стабильному API
  `district.id`, а не только по локализованному названию.
- **Нормо-очки** — нормированный вклад атак игрока с учётом типа района.
- **Коэффициент** — нормо-очки игрока, разделённые на обязательные шесть атак.

## 4. Границы этапа

### 4.1. Входит в этап

- чтение рейдовых сезонов через Clash of Clans API;
- строгая проверка минимального API-контракта;
- агрегация атак до одной строки на игрока;
- новый лист `Рейды`;
- отдельные блоки отслеживаемых кланов;
- профиль системных и пользовательских колонок рейдов;
- наследование совпадающих пользовательских колонок из `Состава`;
- хранение агрегированных сезонов и строк в SQLite;
- показ последнего уикенда между событиями;
- staging-ротация при появлении нового уикенда;
- максимум четыре архивных рейдовых листа;
- удаление самого старого пятого архива;
- сохранение данных удалённого листа в SQLite;
- интеграция в setup, диагностику, auto-fix, `/sync`, `/status` и Telegram-отчёт;
- миграция существующих установок;
- автоматические и ручные проверки.

### 4.2. Не входит в этап

- отдельные листы атак и районов;
- ручное назначение районов игрокам;
- определение «брошенного» района;
- определение кражи добивки;
- штраф или бонус за последний удар по району;
- показ игроков, отсутствующих в `members` API;
- автоматическое восстановление всех пропущенных ботом уикендов;
- средний коэффициент за несколько недель;
- общий рейтинг между несколькими сезонами;
- автоматические наказания, предупреждения или сообщения игрокам;
- автоматический запуск синхронизации по расписанию;
- изменение логики состава и CWL за пределами необходимой интеграции.

## 5. Архитектурные инварианты

Реализация обязана сохранить действующие инварианты проекта, зафиксированные в
`SSOT.md` на проверенном HEAD:

- SQLite остаётся runtime source of truth.
- Google Sheets остаётся пользовательским интерфейсом и хранилищем ручных
  user-values.
- Clash of Clans API остаётся источником технических рейдовых значений.
- Стабильная идентификация строк выполняется через скрытый `__bot_key`.
- Бот управляет только зарегистрированными managed blocks.
- Все данные состава, CWL и рейдов подготавливаются до начала записи.
- Ошибка подготовки рейдов не должна оставлять частично обновлённые листы.
- Невосстановленная ошибка после начала записи Google Sheets должна давать
  существующий partial write warning.
- Chat lock, sheet lock и global semaphore сохраняются.
- `DEV_MODE` не отключает конкурентные блокировки.
- Пользовательская ширина колонок и горизонтальное выравнивание не сбрасываются.
- Служебные идентификаторы листов хранятся и разрешаются по `sheet_id`, а не
  только по названию вкладки.

### 5.1. Намеренные изменения относительно текущего SSOT

Задача расширяет, но не заменяет существующую модель владения данными:

- CoC API становится техническим источником текущих raid season/member/attack
  values;
- SQLite получает raid binding, aggregated row snapshots и bot-owned archive
  registry;
- Google Sheets получает managed active/staging/archive raid areas и остаётся
  источником ручных raid user-values;
- общий `/sync` получает raid preparation и raid write phase;
- `TableType` получает `raids`, а `ColumnValueType` — `number`;
- recoverable pruning failure после успешной ротации становится отдельным
  successful-cleanup-warning, а не общей ошибкой sync.

Остальные владельцы данных, transaction boundaries, access rules и
composition/CWL контракты из SSOT сохраняются. Эти изменения вносятся в
`SSOT.md` только коммитом 8 после реализации и проверки.

## 6. Источник данных и API-контракт

### 6.1. Новый метод клиента

В `ClashClient` добавить метод получения рейдовых сезонов клана:

```text
GET /clans/{encodedClanTag}/capitalraidseasons
```

Метод принимает параметр `limit`. Значение берётся из конфигурации
`RAID_SEASON_FETCH_LIMIT`.

Значение по умолчанию — `5`. Оно используется не для backfill, а для поиска
финального ответа ранее известного active-сезона после простоя бота.

### 6.2. Обязательная проверка ответа

Клиент или рейдовый preparation-слой обязан проверить:

- верхнеуровневый `items` является списком;
- каждый используемый сезон содержит корректные:
  - `state`;
  - `startTime`;
  - `endTime`;
  - `members`;
  - `attackLog`;
- каждый участник содержит:
  - `tag`;
  - `name`;
  - `attacks`;
  - `attackLimit`;
  - `bonusAttackLimit`;
  - `capitalResourcesLooted`;
- каждый используемый район содержит стабильный `id` и список `attacks`;
- каждая атака содержит:
  - атакующего с `tag`;
  - `destructionPercent`;
- `destructionPercent` является целым числом от `0` до `100`;
- числовые значения не являются `bool`;
- теги нормализуются существующим `normalize_tag`;
- количество разобранных атак игрока согласуется с `members[].attacks`.

Если обязательный контракт нарушен, preparation завершается ошибкой до записи
Google Sheets.

Реальный fixture содержит пять `ended` seasons. Ongoing contract tests
применяют
`tests/fixtures/capital_raid_seasons_ongoing.synthetic.json` как overlay к
первому реальному season object с заменой только `state = "ongoing"`. Overlay
проверяет внутреннее ветвление, но не выдаётся за захваченный ongoing
API-ответ.

Несовпадение количества разобранных атак с `members[].attacks` никогда не
принимается как корректная статистика:

- для `ended` это строгая ошибка контракта;
- для `ongoing` это retryable domain error с понятным предложением повторить
  `/sync` позже;
- оба сценария останавливаются на preparation до записи любого листа.

### 6.3. Определение Столицы

Столица определяется по каноническому `district.id = 70000000`, подтверждённому
реальным обезличенным fixture.

Требования:

- ID `70000000` оформляется как именованная протокольная константа;
- источник константы — `tests/fixtures/capital_raid_seasons.json`;
- определение только по полю `name` запрещено;
- район с любым другим корректным `district.id` считается обычным;
- если API обозначает район как `Capital Peak`, но его `district.id` не
  совпадает с подтверждённой константой, preparation завершается ошибкой.

## 7. Выбор отображаемого уикенда

### 7.1. Общие правила

Для каждого активного отслеживаемого клана загружаются последние сезоны в
пределах `RAID_SEASON_FETCH_LIMIT`.

Бот выбирает один отображаемый `season_key` для всей Telegram-группы:

1. Если хотя бы один активный клан имеет `ongoing`-сезон, выбирается его
   `startTime`.
2. Если несколько кланов имеют `ongoing`-сезоны с разными `startTime`, sync
   останавливается до записи.
3. Если текущего сезона нет, выбирается самый новый завершённый сезон среди
   ответов активных кланов.
4. Если API вернул пустую историю, используется последний сохранённый сезон
   этой Telegram-группы и её активных кланов из SQLite.
5. Если нет ни API-сезона, ни сохранённого state, лист показывает понятное
   сообщение об отсутствии данных.

Клан, у которого нет данных выбранного сезона, получает отдельный message-block
`Нет данных рейдового уикенда <период>`.

### 7.2. Пропущенные сезоны

Бот не создаёт листы и строки для промежуточных уикендов, которые никогда не
были его active-сезоном.

Если после простоя найден новый уикенд:

- старый известный active-сезон ищется среди загруженных элементов;
- если найден, его данные финализируются перед архивацией;
- если не найден, архивируется последнее сохранённое состояние и в Telegram
  report добавляется warning;
- промежуточные неизвестные сезоны не восстанавливаются.

## 8. Участники

В таблицу попадают только элементы `members` выбранного сезона.

Следствия принятого правила:

- игрок с нулём атак, отсутствующий в `members`, не показывается;
- текущий состав не используется для добавления нулевых строк;
- ушедший из клана участник сохраняется в сезоне, если он присутствует в API;
- одна строка соответствует одному игровому аккаунту, а не Telegram-пользователю;
- участники разных отслеживаемых кланов выводятся в отдельных клановых блоках.

## 9. Расчёт нормо-очков и коэффициента

### 9.1. Очки одной атаки

Для обычного района:

```text
attack_points = destructionPercent × 2 / 100
```

Для Столицы:

```text
attack_points = destructionPercent × 3 / 100
```

### 9.2. Очки игрока

```text
normal_points = сумма attack_points всех атак игрока
```

Несколько атак одного или разных игроков по одному району учитываются
независимо. Учитывается только разрушение, нанесённое конкретной атакой.

Пример обычного района:

```text
33% → 0,66 нормо-очка
67% → 1,34 нормо-очка
Итого за две атаки → 2,00 нормо-очка
```

Пример Столицы:

```text
40% → 1,20
35% → 1,05
25% → 0,75
Итого → 3,00 нормо-очка
```

### 9.3. Коэффициент игрока

```text
coefficient = normal_points / 6
```

Примеры:

```text
6 нормативных атак → 6,00 / 6 = 1,00
5 нормативных атак → 5,00 / 6 = 0,83
2 нормативные атаки → 2,00 / 6 = 0,33
```

Коэффициент может быть больше `1,00`, если атаки эффективнее нормы.

### 9.4. Точность расчёта

Промежуточный расчёт не должен зависеть от двоичных ошибок `float`.

Рекомендуемое внутреннее значение:

```text
weighted_damage_units =
    Σ(destructionPercent × district_multiplier)
```

где multiplier равен `2` или `3`.

Тогда:

```text
normal_points = weighted_damage_units / 100
coefficient = weighted_damage_units / 600
```

В SQLite сохраняется целочисленный `weighted_damage_units` и исходные
технические значения. В Google Sheets нормо-очки и коэффициент записываются как
числа и отображаются форматом `0.00`.

## 10. Структура листа `Рейды`

### 10.1. Общий макет

Лист строится по существующему CWL-паттерну:

- верхняя строка содержит период и состояние уикенда;
- каждый отслеживаемый клан имеет отдельный managed block;
- в блоке есть название и тег клана;
- первая физическая колонка `__bot_key` скрыта;
- между клановыми блоками сохраняется визуальный отступ;
- обычное структурное оформление заголовков и чередование строк допускается;
- статусные зелёные и жёлтые заливки не добавляются.

Активный лист располагается перед `CWL`, затем идёт `Состав`.

### 10.2. Дефолтные системные колонки

| `column_key` | Заголовок | Тип | Значение |
|---|---|---|---|
| `bot_key` | `__bot_key` | service/string | скрытый стабильный ключ |
| `number` | `№` | system/integer | место в рейтинге |
| `player_name` | `Ник` | system/string | ник из API сезона |
| `player_tag` | `Тег` | system/string | нормализованный тег |
| `attacks` | `Атаки` | system/string | всегда `x/6` |
| `normal_points` | `Нормо-очки` | system/number | вклад с форматом `0.00` |
| `coefficient` | `Выполнение нормы` | system/number | итог с форматом `0%` |
| `capital_resources_looted` | `Золото столицы` | system/integer | формат `#,##0`, в формулу не входит |

`Золото столицы` не участвует в формуле.

Профиль колонок должен поддерживать действующие операции Telegram UI:

- скрытие и показ system-колонок;
- переименование разрешённых колонок;
- изменение порядка;
- создание, переименование, перемещение, скрытие, восстановление и удаление
  user-колонок;
- неизменяемость service-колонки через UI.

### 10.3. Сортировка

Внутри каждого кланового блока строки сортируются:

1. `coefficient` по убыванию;
2. `attacks` по убыванию;
3. `player_name` без учёта регистра по возрастанию;
4. `player_tag` по возрастанию.

`№` — последовательное место после этой сортировки, начиная с `1`. Одинаковые
коэффициенты не создают одинаковые номера.

### 10.4. Подсветка атак

Во время `ongoing`-сезона статусная подсветка не применяется.

После завершения сезона:

- если `attacks < 6`, мягким красным выделяется только ячейка `Атаки`;
- если `attacks >= 6`, статусная заливка отсутствует;
- ячейка `Выполнение нормы` и остальная строка не окрашиваются;
- зелёная и жёлтая статусная заливка не используются.

На архивном листе сохраняется финальное форматирование завершённого сезона.

## 11. Стабильные ключи и user-values

### 11.1. Ключ строки

```text
raid_row:<season_key>|<clan_tag>|<player_tag>
```

`season_key` строится из нормализованного API `startTime`.

Изменение ника, рейтинговой позиции, количества атак или коэффициента не меняет
ключ строки.

### 11.2. Импорт ручных значений

Перед перезаписью active managed blocks бот:

1. читает предыдущие рейдовые managed blocks;
2. находит строки по `__bot_key`;
3. переносит raid user-values;
4. использует SQLite state как fallback;
5. применяет безопасный fallback по техническим полям только при однозначном
   результате;
6. добавляет warning для неоднозначных или повреждённых строк.

### 11.3. Наследование из `Состава`

Поведение должно полностью повторять текущий CWL:

- связываются только активные видимые user-колонки;
- связь определяется по нормализованному title без учёта регистра;
- сначала рассматривается `composition_active`, затем `composition_exited`,
  затем legacy `composition`;
- значение из состава подставляется только в пустое рейдовое user-value;
- заполненное вручную рейдовое значение имеет приоритет;
- изменение состава не перезаписывает непустое рейдовое значение;
- системные колонки по названию не связываются.

При переходе к новому сезону ручные значения старого сезона не переносятся по
старому row key. Новый сезон получает значения из актуального `Состава` только
через описанный механизм совпадающих user-колонок.

## 12. Активный сезон, межсезонье и архивирование

### 12.1. Состояния active-листа

| Состояние | Поведение |
|---|---|
| Есть текущий `ongoing` | показать и обновлять текущий уикенд |
| Текущий завершился | показать финальный уикенд и применить красную подсветку `< 6` |
| Между уикендами | продолжать показывать последний завершённый уикенд |
| Нет API-истории, но есть SQLite state | восстановить последний сохранённый уикенд |
| Нет API-истории и SQLite state | показать message-block об отсутствии данных |

### 12.2. Ротация

Если выбранный `season_key` отличается от сохранённого
`active_raid_season`:

1. Подготовить данные старого и нового сезонов до записи.
2. Если финальный API-ответ старого сезона доступен, обновить старый active-лист
   до финального состояния.
3. Создать staging-лист `Рейды - staging - <sync_run_id>`.
4. Полностью записать и отформатировать новый сезон в staging.
5. Скрыть `__bot_key`.
6. Рассчитать уникальное архивное название старого листа:
   `Рейды YYYY-MM-DD`; при конфликте использовать суффикс ` - N`.
7. Одним `spreadsheets.batchUpdate` переименовать:
   - старый active `Рейды` → архив;
   - staging → `Рейды`.
8. Поставить новый active-лист перед `CWL`.
9. Обновить `_bot_state`, SQLite binding, managed blocks и registry архивов:
   - metadata старых managed blocks перепривязать к архивному имени при
     неизменном `sheet_id`;
   - зарегистрировать архив как bot-owned по `sheet_id` и `season_key`;
   - зарегистрировать managed blocks нового active-листа.
10. Выполнить ограничение количества архивов.

Если `active_raid_season` отсутствует, message-only лист не архивируется:
первый найденный сезон становится active.

### 12.3. Ограничение архивов

- Максимум архивных рейдовых листов — `4`.
- Active-лист `Рейды` в лимит не входит.
- После успешной ротации определяется количество зарегистрированных архивов.
- Если архивов стало больше четырёх, самые старые удаляются последовательно,
  пока количество не станет равно лимиту.
- Старый архив определяется по каноническому `season_start_at`, затем по
  `archived_at`, а не по позиции или вручную изменённому названию.
- Удаляется только архив, зарегистрированный самим ботом и найденный по
  сохранённому `sheet_id`.
- Вкладка с совпадающим названием, но без bot registry, автоматически не
  удаляется.
- После удаления вкладки удаляются её archive registry и managed-block metadata.
- `raid_player_state` удалённого сезона сохраняется без срока.
- При ошибке удаления новый active и новый архив не откатываются;
  `sync_runs.status` и `last_sync_status` остаются `success`;
  Telegram report получает отдельный cleanup warning, а pruning повторяется
  при следующем `/sync`.
- Recoverable pruning warning не использует общий текст
  `Таблица могла быть частично обновлена`: active data уже успешно записаны, а
  незавершён только retention cleanup.

## 13. SQLite

### 13.1. Изменение типов

В `TableType` добавить:

```text
raids
```

В `ColumnValueType` добавить числовой тип для дробных значений:

```text
number
```

Он используется для `Нормо-очки` и `Коэффициент`. Эти значения должны
записываться в Google Sheets как числа, а не как строки с запятой или
добавленным символом.

### 13.2. Расширение sheet binding

Добавить raid-поля:

```sql
active_raid_sheet_name TEXT NOT NULL DEFAULT 'Рейды'
active_raid_sheet_id INTEGER
active_raid_season TEXT
```

Имя обязательно и доступно до создания физического листа. `sheet_id` и
`season` остаются nullable. Для новых binding:

```text
active_raid_sheet_name = "Рейды"
active_raid_sheet_id = созданный sheet_id
active_raid_season = NULL
```

### 13.3. Таблица агрегированных строк

Добавить `raid_player_state`:

```text

chat_id
season_key
season_start_at
season_end_at
season_state
row_key
clan_tag
player_tag
technical_values_json
user_values_json
row_hash
updated_at
```

Ограничение:

```text
UNIQUE(chat_id, season_key, row_key)
```

Индекс:

```text
(chat_id, season_key, clan_tag)
```

`technical_values_json` минимум содержит:

```text
player_name
attacks
attack_limit
bonus_attack_limit
capital_resources_looted
weighted_damage_units
normal_points
coefficient
```

### 13.4. Registry архивов

Добавить `raid_sheet_archives`:

```text
id
chat_id
season_key
season_start_at
sheet_name
sheet_id
archived_at
```

Ограничения:

```text
UNIQUE(chat_id, season_key)
UNIQUE(chat_id, sheet_id)
```

Индекс:

```text
(chat_id, season_start_at, archived_at)
```

Registry используется для безопасного pruning и диагностики. Название листа не
является единственным идентификатором.

### 13.5. Column profiles

Для всех существующих и новых Telegram-групп должны быть созданы default
profiles `raids`.

Миграция:

- идемпотентна;
- использует стабильные `column_key`;
- не изменяет существующие profiles состава и CWL;
- не удаляет пользовательские данные;
- повторный запуск безопасен.

### 13.6. Retention

SQLite state рейдов автоматически не очищается.

Удаление архивной вкладки Google Sheets не удаляет:

- агрегированные технические значения сезона;
- user-values сезона;
- row hashes.

## 14. `_bot_state`

Повысить версию схемы `_bot_state`.

Добавить:

```text
active_raid_sheet_name
active_raid_sheet_id
active_raid_season
```

Требования совместимости:

- старый `_bot_state` без рейдовых полей читается как legacy;
- отсутствие рейдовых полей является fixable issue, а не необратимой ошибкой;
- auto-fix создаёт или разрешает `Рейды`, записывает новые поля и сохраняет

- `_bot_state` остаётся скрытым.

### 15.1. Новая привязка

При инициализации новой таблицы обязательны:

- `Состав`;
- `CWL`;
- `Рейды`;
- `_bot_state`.

После выдачи доступа бот:

- создаёт отсутствующие листы;
- сохраняет все `sheet_id`;
- создаёт default column profiles, включая `raids`;
- скрывает служебные области;
- завершает binding только после успешной проверки.

### 15.2. Telegram UI колонок

В раздел настроек добавить:

```text
Колонки рейдов
```

Payload должен использовать короткий стабильный код, укладывающийся в лимит
Telegram callback data.

Все проверки fresh admin access, setup-state ownership и text completion
должны повторять действующие правила остальных column profiles.

## 16. Диагностика и auto-fix

Диагностика должна проверять:

- наличие active-листа `Рейды`;
- соответствие сохранённого `sheet_id`;
- наличие рейдовых полей в `_bot_state`;
- наличие service-колонки `__bot_key` в active managed blocks;
- скрытие `__bot_key`;
- валидность зарегистрированных managed blocks;
- наличие зависших staging-листов;
- соответствие archive registry фактическим листам;
- превышение лимита зарегистрированных архивов;
- отсутствие попытки удалить незарегистрированный лист.

Auto-fix может:

- создать отсутствующий active-лист;
- восстановить binding по каноническому листу;
- записать недостающие `_bot_state` поля;
- скрыть `__bot_key`;
- удалить безопасно распознанные зависшие staging-листы по существующим
  правилам;
- очистить registry записи для уже отсутствующих архивов;
- повторить pruning зарегистрированных архивов.

Auto-fix не должен:

- удалять неизвестные пользовательские листы;
- считать лист архивом только по названию;
- восстанавливать пропущенные сезоны;
- менять техническую статистику без успешного CoC API preparation.

## 17. Интеграция в `/sync`

Новый pipeline:

```text
start sync run
    ↓
load RuntimeChatConfig
    ↓
prepare composition
    ↓
prepare CWL
    ↓
prepare raids
    ↓
write composition
    ↓
write CWL
    ↓
write raids
    ↓
write SQLite state
    ↓
commit SQLite
    ↓
send Telegram report
```

Требования:

- `prepare raids` получает подготовленные состояния состава для наследования
  user-values;
- ни один лист не записывается до успешного завершения всех трёх preparation;
- рейдовый write phase получает отдельное диагностическое имя;
- ошибка рейдовой записи после composition/CWL write добавляет partial write
  warning;
- SQLite commit выполняется после Google Sheets write;
- ошибка отправки Telegram report после commit не откатывает success;
- cooldown и locks остаются общими для всего `/sync`.

## 18. Конфигурация

Добавить переменные:

```env
RAID_ARCHIVE_SHEETS_LIMIT=4
RAID_ATTACKS_TARGET=6
RAID_NORMAL_DISTRICT_ATTACK_NORM=2
RAID_CAPITAL_DISTRICT_ATTACK_NORM=3
RAID_SEASON_FETCH_LIMIT=5
RAID_API_CONCURRENCY_LIMIT=5
```

Требования:

- значения читаются через существующий config loader;
- лимиты и нормы должны быть положительными целыми числами;
- `RAID_SEASON_FETCH_LIMIT` должен быть не меньше `2`;
- неверное значение вызывает `ConfigError` при запуске;
- production-логика не содержит продублированных magic numbers;
- `6`, `2`, `3` и `4` используются как значения по умолчанию и принятая
  политика, но расчёт получает их из `AppConfig`.

Видимое `x/6`, знаменатель коэффициента и правило красной подсветки используют
одно значение `RAID_ATTACKS_TARGET`.

## 19. Telegram-отчёт

Успешный report дополняется секцией `Рейды`.

Для active/завершённого сезона показывать:

- период;
- состояние: проводится / завершён / показан сохранённый;
- количество клановых блоков;
- количество участников;
- количество игроков с `6/6`;
- количество игроков с `< 6/6` после завершения;
- факт архивации предыдущего сезона;
- название созданного архива;
- факт и название удалённого старого архива;
- предупреждение, если старый active-сезон архивирован из последнего
  сохранённого state без финального API-ответа;
- warnings импорта user-values.

Если данных нет:

```text
Рейды сейчас не проводятся. Сохранённых данных за прошлый уикенд нет.
```

Report должен соблюдать `REPORT_MAX_ITEMS` и существующее HTML-экранирование.

## 20. Ошибки и крайние случаи

### 20.1. Ошибки до записи

Без изменения Google Sheets завершаются:

- недоступность CoC API;
- битый JSON;
- отсутствие обязательного API-поля;
- противоречивый `district.id` района `Capital Peak`;
- несогласованные сезоны активных кланов;
- несовпадение `members[].attacks` и разобранного attack log;
- повреждённый SQLite technical state;
- неоднозначный active-лист;
- ошибка импорта обязательных managed blocks.

### 20.2. Ошибки после начала записи

Дают partial write warning:

- ошибка форматирования active/staging;
- ошибка атомарной ротации;
- ошибка `_bot_state` write;
- ошибка SQLite binding/state write после изменения Google Sheets.

Ошибка удаления лишнего зарегистрированного архива после успешной ротации
является исключением: она перехватывается как recoverable cleanup warning,
сохраняет успешный status и повторяется при следующем sync.

### 20.3. Безопасное восстановление

Resolver active-листа должен учитывать частичную ротацию:

- канонический `Рейды` предпочтительнее устаревшего `sheet_id`, указывающего на
  архив;
- staging не считается active;
- archive registry разрешается по `sheet_id`;
- повторный `/sync` должен завершить metadata/state reconciliation без
  повторного архивирования того же сезона.

### 20.4. Ручные правки

- ручное изменение технических значений исправляется следующим `/sync`;
- ручные user-values сохраняются;
- ручное изменение title archive-листа не лишает его bot identity;
- ручное удаление archive-листа фиксируется диагностикой;
- ручное удаление active-листа является fixable issue;
- изменение ширины и горизонтального выравнивания сохраняется;
- служебная первая колонка после sync снова скрывается.

## 21. Миграция существующих установок

Миграция должна:

1. Повысить `SCHEMA_VERSION`.
2. Добавить обязательное raid sheet name и nullable raid sheet ID/season.
3. Создать `raid_player_state`.
4. Создать `raid_sheet_archives`.
5. Добавить default `raids` column profiles всем существующим чатам.
6. Не создавать фиктивные сезоны или строки.
7. Не удалять CWL/composition state.
8. Не требовать ручного редактирования `bot.db`.

После миграции первый `/sync`:

- находит или создаёт `Рейды`;
- обновляет `_bot_state`;
- получает самый свежий доступный уикенд;
- не создаёт архивы пропущенных уикендов;
- не считает отсутствие старого raid state ошибкой.

Перед production-обновлением сохраняется действующее требование backup
`bot.db`.

## 22. Автоматические тесты

### 22.1. Config

- значения по умолчанию;
- валидные пользовательские значения;
- пустые и отсутствующие значения;
- ноль, отрицательные и нечисловые значения;
- `RAID_SEASON_FETCH_LIMIT < 2`.

### 22.2. API client и parser

- URL encoding clan tag;
- query `limit`;
- пустой `items`;
- текущий и завершённый сезон;
- несколько сезонов;
- malformed member/district/attack;
- `bool` вместо числа;
- произвольный non-Capital district ID классифицируется как обычный;
- конфликт названия `Capital Peak` и подтверждённого district ID;
- нормализация player tags;
- ended mismatch количества атак как strict contract error;
- ongoing mismatch как retryable domain error до write.

### 22.3. Формула

- обычный район `33% + 67%` даёт `2,00` нормо-очка;
- Столица `40% + 35% + 25%` даёт `3,00`;
- смешанные районы одного игрока;
- несколько игроков на одном районе;
- одна сильная атака;
- шесть нормативных атак дают `K = 1,00`;
- пять нормативных атак дают `K = 0,83` при отображении с двумя знаками;
- коэффициент больше единицы;
- отсутствие специальных очков за добивку;
- отсутствие float drift.

### 22.4. Участники и сортировка

- выводятся только `members`;
- игрок состава без `members` не добавляется;
- игрок API, отсутствующий в текущем составе, сохраняется;
- сортировка по коэффициенту;
- tie-break по атакам, нику и тегу;
- последовательный `№`.

### 22.5. User-values

- exact `__bot_key`;
- безопасный fallback;
- перенос значения из предыдущего active-листа;
- восстановление из SQLite;
- совпадающий title с составом;
- пустое raid value заполняется из состава;
- непустое raid value не перезаписывается;
- регистр и пробелы title нормализуются;
- системные колонки не связываются.

### 22.6. Форматирование

- `Атаки` всегда `x/6`;
- ongoing `< 6` не окрашивается;
- ended `< 6` окрашивает только ячейку `Атаки`;
- ended `6/6` не получает статусной заливки;
- коэффициент и нормо-очки остаются числовыми;
- ручное горизонтальное выравнивание сохраняется;
- `__bot_key` скрывается.

### 22.7. Межсезонье и ротация

- текущий сезон;
- завершение того же сезона без ротации;
- показ последнего завершённого;
- восстановление из SQLite при пустом API items;
- staging нового сезона;
- атомарное переименование двух листов;
- уникальное archive title;
- resolver после частичной ротации;
- отсутствие backfill промежуточных сезонов;
- финализация старого active из API;
- warning при отсутствии финального API-ответа.

### 22.8. Retention

- четыре архива сохраняются;
- пятый приводит к удалению только самого старого;
- active-лист не входит в лимит;
- выбор по season metadata, а не названию;
- незарегистрированный лист не удаляется;
- SQLite player state старого сезона сохраняется;
- отсутствующий вручную архив очищается из registry через auto-fix;
- ошибка удаления даёт specific cleanup warning при successful sync и
  допускает повторный pruning.

### 22.9. Общий `/sync`

- все preparation выполняются до первой записи;
- raid preparation error не меняет ни один лист;
- raid write error после предыдущих writes даёт partial warning;
- успешный commit и Telegram delivery failure;
- chat/sheet/global locks;
- `DEV_MODE` отключает только cooldown.

### 22.10. Migration и setup

- миграция существующей v3 базы;
- повторная миграция;
- default raid columns для существующего чата;
- новая binding создаёт четыре обязательных листа;
- legacy `_bot_state` диагностируется и исправляется;
- transfer flow переносит raid state, profiles, blocks, binding и archive registry.

## 23. Ручная проверка

1. Сделать backup production `bot.db`.
2. Развернуть версию в dev-конфигурации с `DEV_MODE=True`.
3. Подключить новую тестовую Google-таблицу.
4. Проверить создание `Состав`, `CWL`, `Рейды`, `_bot_state`.
5. Добавить кланы и выполнить `/sync`.
6. Проверить отдельный блок каждого клана.
7. Сверить нескольких игроков с API:
   - атаки;
   - золото;
   - нормо-очки;
   - коэффициент.
8. Проверить пример обычного района `33% + 67%`.
9. Во время текущего уикенда убедиться, что `5/6` не красится.
10. После завершения повторить `/sync` и убедиться, что красится только ячейка
    `Атаки` со значением меньше `6/6`.
11. Создать одинаковую user-колонку в `Составе` и `Рейдах`.
12. Проверить заполнение пустого значения из состава.
13. Изменить значение вручную в рейдах и убедиться, что `/sync` его не затирает.
14. Изменить ширину и горизонтальное выравнивание, повторить `/sync`.
15. При новом уикенде проверить:
    - staging;
    - архив предыдущего;
    - новый canonical `Рейды`;
    - позицию перед `CWL`.
16. Последовательно получить пять архивов и убедиться, что остаются четыре
    самых новых.
17. Убедиться, что удалённый из Sheets сезон остаётся в SQLite.
18. Пропустить один или несколько уикендов и убедиться, что промежуточные архивы
    не создаются.
19. Имитировать ошибку API до write и проверить неизменность всех листов.
20. Имитировать ошибку pruning и проверить successful status, specific cleanup
    warning, сохранённый registry и успешный повторный pruning.
21. Проверить `/status`, Telegram report, диагностику и auto-fix.
22. Запустить полный набор автоматических проверок.

## 26. Критерии приёмки

Задача считается выполненной, если:

1. `/sync` создаёт и обновляет `Рейды` без порайонных листов.
2. В строках присутствуют только участники API.
3. Формула использует нормы `2`, `3` и знаменатель `6` из конфигурации.
4. Шесть нормативных атак дают коэффициент `1,00`.
5. Таблица сортируется по коэффициенту по убыванию.
6. `Атаки` всегда отображаются как `x/6`.
7. Во время ongoing-сезона статусной красной заливки нет.
8. После завершения `< 6/6` красит только ячейку `Атаки`.
9. Общие user-колонки ведут себя так же, как в CWL.
10. Между событиями показывается последний завершённый сезон.
11. При новом сезоне старый active архивируется через staging-ротацию.
12. Одновременно существует не более четырёх зарегистрированных архивов.
13. Пятый архив удаляет только самый старый bot-owned лист.
14. Удаление вкладки не удаляет агрегированный SQLite state.
15. Пропущенные промежуточные уикенды не восстанавливаются.
16. Старые composition/CWL данные и поведение не повреждаются.
17. Preparation error не меняет Google Sheets.
18. Невосстановленная ошибка после начала write даёт partial write warning.
19. Диагностика и auto-fix понимают рейдовый binding.
20. Все целевые и полные проверки проходят.
21. Последний коммит плана актуализирует `SSOT.md` по фактически реализованным
    владельцам данных, snapshots, fallback, pipeline и инвариантам рейдов.
22. Recoverable pruning failure завершает sync успешно со специальным cleanup
    warning и повторяется при следующем запуске.

## 27. Риски и принятые ограничения

- Игрок с нулём атак может отсутствовать в `members` и не попасть в таблицу. Это
  принято сознательно.
- Игрок с полезной небольшой добивкой получает мало нормо-очков. Специальная
  компенсация не вводится.
- Игрок, не заработавший бонусную атаку, всё равно считается не выполнившим
  требование `6/6`. Это принято сознательно.
- При длительном простое старый active-сезон может исчезнуть из доступного
  API-окна. Тогда архив строится из последнего сохранённого state с warning.
- Google Sheets и SQLite не образуют общей транзакции. Риски компенсируются
  staging, атомарным rename, canonical resolver, registry и partial warning.
- Старый SQLite state растёт без автоматического удаления, но хранит только
  агрегированные строки игроков и имеет малый ожидаемый объём.
- Повреждение или ручное удаление вкладок исправляется только в пределах
  безопасно идентифицированных bot-owned объектов.
