# Инструкция Codex по выполнению задачи

## Назначение

Этот файл задаёт рабочий протокол для Codex. Источником продуктовых требований
остаётся `requirements.md`, а не этот документ.

## Стартовая проверка

Перед каждым продуктовым коммитом Codex сообщает:

1. текущие ветку и HEAD;
2. состояние `git status`;
3. какой пункт `commit-plan.md` выполняется;
4. какие файлы и тесты относятся к пункту;
5. как он понял границы;
6. риски, противоречия и отсутствующие данные.

Если рабочее дерево содержит чужие изменения в затрагиваемых файлах, Codex не
перезаписывает их и запрашивает решение.

Списки файлов в `commit-plan.md` являются ожидаемыми, но не исчерпывающими.
Перед изменением дополнительного файла Codex объясняет необходимость и
проверяет, что изменение не выходит за scope текущего коммита.

## Обязательное чтение

Перед каждым пунктом:

```text
docs/tasks/raids/README.md
docs/tasks/raids/requirements.md
docs/tasks/raids/decisions.md
docs/tasks/raids/architecture.md
соответствующий раздел docs/tasks/raids/commit-plan.md
соответствующие разделы docs/tasks/raids/verification.md
SSOT.md
tests/fixtures/capital_raid_seasons.json
tests/fixtures/capital_raid_seasons_ongoing.synthetic.json
актуальные исходники и тесты пункта
```

`SSOT.md` используется как baseline уже реализованной системы. До коммита 8
его нельзя менять для описания будущего рейдового поведения.

## Единица работы

Одна сессия реализации — один продуктовый коммит.

Codex не должен:

- начинать следующий пункт;
- добавлять удобный несвязанный рефакторинг;
- заранее менять setup, reports или SSOT;
- создавать commit или push без разрешения;
- менять зафиксированные решения без отдельного согласования;
- менять подтверждённый fixture Capital Peak ID `70000000` без нового реального
  API evidence;
- маскировать failing test удалением или ослаблением проверки.

## Правила кода

- Python 3.12.
- Полные type hints.
- Русские Google-style docstring.
- Русские комментарии только там, где они объясняют неочевидный контракт.
- Config вместо бизнес-литералов.
- Strict parsing внешних данных.
- `bool` не считается допустимым `int`.
- Stable keys вместо nickname, номера строки и названия вкладки.
- Подготовка всех доменов до Sheet write.
- Только bot-owned managed blocks и зарегистрированные archive sheet IDs.
- Существующие composition/CWL контракты сохраняются.

## Ограничение тестового sandbox

На базовом HEAD полный suite вне Codex sandbox подтверждён:

```text
.venv/bin/python -m pytest -q
94 passed in 0.93s
```

Внутри sandbox `aiosqlite` worker thread может не пробудить asyncio event loop.
Codex не объявляет такой зависший запуск ни success, ни test failure:

1. фиксирует последний начатый тест;
2. запускает доступные non-SQLite проверки;
3. просит пользователя повторить точную SQLite/full-suite команду вне sandbox;
4. включает пользовательский результат в отчёт без искажения.

## Формат отчёта до изменений

```text
Коммит плана:
Известно:
Прочитаны файлы:
Задача пункта:
Затрагиваются:
Риски и неизвестные:
План проверки:
```

Если неизвестное влияет на реализацию, Codex задаёт один минимальный набор
вопросов и ждёт ответа.

## Формат результата

После изменений Codex предоставляет:

1. полный unified diff от корня репозитория;
2. перечень изменённых и новых файлов;
3. объяснение, почему затронут каждый файл;
4. выполненные команды;
5. точные результаты тестов;
6. ручной сценарий проверки текущего пункта;
7. возможные регрессии;
8. то, что осталось за пределами пункта;
9. предлагаемое commit message;
10. ожидание подтверждения перед commit.

Нельзя писать «все тесты прошли», если запускались только выбранные тесты.

## Шаблон задания на следующий пункт

```text
Выполни только коммит <N> из
docs/tasks/raids/commit-plan.md.

Перед изменениями:
- проверь HEAD, ветку и git status;
- прочитай все документы из docs/tasks/raids/;
- прочитай SSOT.md как baseline текущей системы;
- открой актуальные исходники и тесты этого пункта;
- перечисли известное, границы, риски и неизвестные.

Не выполняй будущие пункты и не меняй SSOT.md до коммита 8.
Не создавай commit и не делай push без моего отдельного разрешения.

После реализации покажи полный unified diff, запусти проверки пункта,
git diff --check и дождись подтверждения.
```

## Шаблон проверки готового пункта

```text
Проверь реализацию коммита <N> относительно:
- docs/tasks/raids/requirements.md;
- docs/tasks/raids/decisions.md;
- docs/tasks/raids/architecture.md;
- раздела коммита <N> в commit-plan.md;
- соответствующих проверок verification.md;
- текущего SSOT.md.

Не исправляй найденные проблемы без моей команды.
Сначала дай findings по критичности с файлами, причиной, риском и
минимальным способом исправления.
```

## Шаблон разрешения на commit

После проверки пользователь может дать отдельную команду:

```text
Создай только commit <N> с согласованным сообщением.
Не делай push и не начинай следующий пункт.
```

Перед commit Codex повторно проверяет `git diff --check`, убеждается, что staged
scope соответствует пункту, и не добавляет посторонние файлы.

## Специальное правило коммита 8

До коммита 8 Codex проверяет фактическую реализацию коммитов 1–7 и результаты
ручного smoke.

При обновлении `SSOT.md`:

- описывается только существующий код;
- названия таблиц, полей и pipeline сверяются с реализацией;
- recoverable pruning описывается по фактической семантике;
- будущий средний рейтинг не упоминается как реализованный;
- task docs переводятся в завершённый статус только после всех проверок.
