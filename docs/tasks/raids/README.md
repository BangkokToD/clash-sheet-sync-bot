## Документы задачи

1. [`requirements.md`](requirements.md) — утверждённое техническое задание и
   критерии приёмки.
2. [`decisions.md`](decisions.md) — закрытые продуктовые и архитектурные
   решения. Codex не должен повторно выбирать эти варианты.
3. [`architecture.md`](architecture.md) — целевая архитектура, владение
   данными, поток `/sync` и карта затрагиваемых файлов.
4. [`commit-plan.md`](commit-plan.md) — исполняемый план коммитов с границами,
   тестами и условиями завершения каждого шага.
5. [`verification.md`](verification.md) — матрица автоматических и ручных
   проверок.
6. [`codex.md`](codex.md) — правила выполнения плана и шаблон задания Codex на
   один коммит.

Документы разделяют текущее и целевое состояние:

- актуальный корневой `SSOT.md` определяет текущее реализованное поведение и
  все действующие контракты, которые задача явно не меняет;
- `requirements.md` — единственный нормативный источник целевого продуктового
  поведения и критериев приёмки рейдов;
- `decisions.md` фиксирует причины закрытых решений и не переопределяет
  детальные контракты `requirements.md`;
- `architecture.md` описывает способ реализации требований;
- `commit-plan.md`, `verification.md` и `codex.md` не создают новых требований.

Намеренные изменения относительно текущего SSOT перечислены отдельно в
`requirements.md`. Любой другой конфликт нельзя разрешать молча: до изменения
кода Codex должен остановиться, описать расхождение и запросить решение.

## Как начать

До первого кодового коммита нужны:

1. утверждённые task-docs;
2. чистая или понятная рабочая ветка от указанного HEAD;
3. отдельный предварительный docs-коммит с этим каталогом и fixtures.

Перед применением migration к рабочей SQLite отдельно требуется backup базы с
учётом WAL. Для коммита 1, который не меняет SQLite, production backup не
нужен.

Рекомендуемое название предварительного коммита:

```text
docs: add raid implementation task
```

Он не входит в восемь продуктовых коммитов и не изменяет `SSOT.md`.

## Правило выполнения

Codex выполняет только один пункт `commit-plan.md` за раз.

Перед каждым пунктом он обязан:

1. проверить текущие HEAD, ветку и `git status`;
2. перечитать этот файл, `requirements.md`, `decisions.md` и соответствующий
   раздел `commit-plan.md`;
3. открыть все актуальные файлы, которые собирается менять;
4. перечислить известное, затрагиваемые части системы, риски и неизвестные;
5. остановиться, если fixture отсутствует/не проходит contract validation или
   найдено противоречие.

После реализации пункта Codex:

1. показывает полный unified diff;
2. запускает целевые проверки пункта;
3. запускает `git diff --check`;
4. сообщает результат и оставшиеся ограничения;
5. не начинает следующий пункт и не создаёт commit без отдельной команды.

## Общие запреты

- Не реализовывать будущие пункты плана «заодно».
- Не изменять формулу, правила подсветки, состав участников и retention.
- Не добавлять порайонные или поатаковые пользовательские листы.
- Не делать backfill пропущенных уикендов.
- Не обновлять `SSOT.md` до коммита 8.
- Не хардкодить на уровне бизнес-логики значения, вынесенные в `AppConfig`.
- Не угадывать `Capital Peak` по локализованному имени.
- Не удалять вкладки, не зарегистрированные как bot-owned по `sheet_id`.
- Не скрывать partial-write сценарии и специальные cleanup warnings при
  recoverable pruning.
- Не выполнять commit, push, reset или удаление пользовательских файлов без
  прямого разрешения.

## Готовность задачи

- выполнения коммитов 1–8 по порядку;

- ручной проверки из `verification.md`;
- применения миграции на копии production-базы;
- актуализации `SSOT.md` последним коммитом;
- проверки, что старое поведение состава и CWL не изменилось.
